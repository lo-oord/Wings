# أدوات المالك — دليل التشغيل

هذا المستند يشرح الخطوات اليدوية الوحيدة المطلوبة بعد نشر الكود، والبنية التي
أضافتها أدوات المالك، والحدود المفروضة على الخطة المجانية.

---

## 1. تعيين المالك (خطوة واحدة في Firebase Console)

لا يمكن لأي عميل منح نفسه صلاحية. الصلاحية تُقرأ من مستند واحد فقط:

```
staff/{UID_الخاص_بحسابك}
{
  "role": "owner",
  "updatedAt": <server timestamp>
}
```

الخطوات:

1. افتح Firebase Console → Firestore Database.
2. أنشئ مجموعة باسم `staff` (بالحروف اللاتينية الصغيرة).
3. أنشئ داخلها مستندًا معرّفه هو **UID حسابك** (من Authentication → Users).
4. أضف الحقل `role` بالقيمة `owner` (سلاسل نصية فقط: `owner` أو `admin` أو `moderator`).
5. أعد تشغيل التطبيق وسجّل الدخول بحسابك: يظهر قسم «المطوّر» في الإعدادات.

> المستند قابل للقراءة من حسابك فقط، والكتابة عليه من التطبيق ممنوعة تمامًا.
> المالك يستطيع منح `moderator` أو `admin` لحساب آخر، أما `owner` فلا يُمنح
> إلا من الـ Console — وهذا ما يمنع تصعيد الصلاحيات.

قواعد Firestore تتحقق من الدور في **كل عملية كتابة إدارية**، لذا إخفاء الواجهة
ليس حد الأمان.

## 2. نشر القواعد والفهارس

```bash
firebase deploy --only firestore:rules
firebase deploy --only firestore:indexes
```

أو انسخ محتوى `firestore.rules` و`firestore.indexes.json` إلى المستودع وانشرهما
من لوحة Firebase. الفهارس المركّبة المطلوبة:

| المجموعة | الحقول |
| --- | --- |
| `users` | `status` ASC, `createdAt` DESC |
| `users` | `status` ASC, `createdAt` ASC |
| `reports` | `status` ASC, `createdAt` DESC |

باقي الاستعلامات تستخدم الفهارس التلقائية لحقل واحد.

## 3. البنية المضافة

| المسار | الغرض | من يقرأ | من يكتب |
| --- | --- | --- | --- |
| `staff/{uid}` | الدور الموثوق | الحساب نفسه / المالك | Console، أو مالك لحساب آخر |
| `users/{uid}/admin/status` | حالة الحساب والقيود | الحساب نفسه + الطاقم | `admin`/`owner` |
| `users/{uid}/warnings/{id}` | سجل التحذيرات (لا يُحذف عند الإلغاء) | الحساب نفسه + الطاقم | `admin`/`owner` |
| `users/{uid}/ownerMessages/{id}` | نسخة المستلم الخاصة من رسالة المالك | المستلم + الطاقم | `admin`/`owner` |
| `ownerMessages/{id}` | فهرس رسائل المالك للطاقم | الطاقم | `admin`/`owner` |
| `users/{uid}/notifications/{id}` | الإشعارات الرسمية (`type: admin`) | المستلم | المستلم للرد، والطاقم للإشعار الرسمي |
| `adminLog/{id}` | سجل النشاط الإداري | الطاقم | الطاقم — **لا تعديل ولا حذف لأي طرف** |
| `reports/{id}` | البلاغات (المجموعة الموجودة) | الطاقم | العضو عند الإنشاء، الطاقم عند المراجعة |
| `appeals/{id}` | طلبات المراجعة | صاحبها + الطاقم | صاحبها عند الإنشاء، الطاقم للقرار |
| `emailBlocks/{بريد-موحّد}` | حظر بريد (بدون تخزين نسخة من البريد) | `get` فقط لمن يعرف البريد | `admin`/`owner` فقط (السرد ممنوع) |
| `blockedUsernames/{اسم-موحّد}` | حظر اسم مستخدم | `get` فقط | `admin`/`owner` فقط |
| `announcements/{id}` | إعلانات عامة | كل مستخدم مسجّل | `admin`/`owner` |
| `systemMonitor/{sourceId}` | آخر نتيجة فحص مصدر | `admin`/`owner` | `admin`/`owner` |

### كيف تنتهي العقوبات؟

لا يوجد جدولة (scheduled functions). القيود تعتمد على مقارنة `request.time`
داخل القواعد نفسها:

- إيقاف مؤقت → `expiresAt` في `users/{uid}/admin/status`.
- قيد ميزة → `restrictionsExpireAt`.
- بعد انتهاء الوقت تصبح القاعدة غير مفعّلة تلقائيًا، دون أن يفتح المستخدم
  التطبيق، ودون أي عملية تنظيف يمكن أن تفشل.
- التطبيق يعرض الحالة الفعلية عبر `effectiveState()` ويحوّل الإيقاف المنتهي إلى
  «نشط» أو «مقيّد» حسب ما تبقى من قيود.

## 4. حدود الخطة المجانية

1. **حذف حساب Auth لشخص آخر** غير ممكن من العميل بدون Admin SDK (يتطلب خطة
   مدفوعة/خدمة خلفية). البديل المنفّذ: حذف كل بيانات Firestore والملف العام
   والتعليقات وحجز الاسم، ووضع الحالة `deleted`. قواعد الأمان ترفض بعد ذلك كل
   كتابة من الحساب، والتطبيق يخرجه إلى شاشة الحالة. الحساب في Authentication
   يبقى موجودًا (لا يستطيع استخدام Wings).
2. **حظر البريد قبل إنشاء حساب Firebase Auth** غير ممكن تقنيًا بدون خادم.
   التنفيذ: فحص مسبق من العميل عبر `get` على مستند واحد، ثم **منع إنشاء مستند
   الحساب** في القواعد اعتمادًا على `request.auth.token.email`. النتيجة: بريد
   محظور لا يستطيع إكمال حساب قابل للاستخدام حتى لو نادى Auth API مباشرة.
3. **الإشعارات العامة** تُقرأ من مستند مشترك بدل كتابة نسخة في `notifications`
   لكل عضو (آلاف الكتابات). تُعرض داخل مركز الإشعارات، وتُحفظ حالة القراءة في
   `users/{uid}/meta/announcements` لكل حساب على حدة.
4. **الفحص الصحي** يعمل عند الضغط فقط، طلب واحد صغير لكل مصدر، ويُخزَّن آخر
   نتيجة. لا فحص دوري كي لا نستهلك الحصة ولأنه لا يمكن جدولته مجانًا.

## 5. ما تحقّق فعليًا

- `flutter analyze` → لا أخطاء ولا تحذيرات.
- `flutter test` → 94 اختبارًا ناجحًا (80 القديمة + 14 جديدة لحالات الحساب).
- بناء APK يُنفَّذ عبر GitHub Actions عند الدفع (لا تتوفر أدوات Android SDK في
  بيئة التحرير)، والـ Workflow يبني أربع حزم APK و AAB.
